Grading Submission

How a raw card becomes a graded slab without losing its cost basis along the way.

1. Build the batch

Grading → Submissions → New Batch.

  • Pick a grading company (PSA, BGS, CGC, ARS, TAG, ACE).
  • Set service level + grading cost per card (what the grader is charging you).
  • Add cards from your raw_for_sale and inspected inventory. Filter by decision = "submit to grading" to find cards routed for it.

When you add a card, its quantity is decremented from the source raw row and added to a new grading_submitted row tied to the batch. The original cost follows along.

2. Ship + track

Mark the batch shipped when it leaves your hands. Add the tracking number, any sub-batch ID the grader assigned, and the expected return date.

While in flight, those cards show as grading_submitted in inventory — visible in Pipeline but not in raw_for_sale lists or in graded inventory yet.

3. Process the return

When PSA / BGS / etc. emails the return CSV:

  1. Grading → Submissions → [your batch] → Process Return.
  2. Upload the CSV. Reactor matches each return row to a batch item using:
    • Card name substring match
    • Card # match (extracted from PSA's Description column)
    • Set name token overlap
    • Year match
    • Language match
    • Line position
  3. Review the slot list. Each match has a confidence score: Strong / Good / Weak / Manual.
  4. For each slot, set the disposition:
    • graded (default) — creates a new slab. Requires cert # + grade.
    • not_graded — card came back ungraded. Creates a new raw row in inventory with cost = original + grading_cost.
    • lost — write-off. No new row.
    • not_submitted — never actually shipped. Creates a new raw row with cost = original only.
  5. Confirm. Slabs are created with the right cost basis (raw_cost + grading_cost), the original raw row is decremented, and the batch is marked returned.

4. After the fact

If the grader corrects an invoice (you got a different total than expected), edit the batch's grading_cost. The change fans out to:

  • All slabs linked to the batch get their grading_cost updated.
  • All historical sales of those slabs get their total_cost_basis recomputed. Profit reports stay accurate.

Legacy slabs (created before migration 056) have NULL grading_batch_id and stay frozen at their snapshot value.

Reverting a batch

Grading → Submissions → [batch] → Delete Batch.

If the batch was returned: every slab is removed (unless sold or actively listed) and the source raw cards are restored from the audit log. Sold/listed slabs stay intact — you'd lose revenue records otherwise — and you'll see a warning telling you how many were kept.

If the batch was still pending: easier. Cards are routed back to their pre-submission state.
