Raw Card Flow

The raw card lifecycle from purchase to sale (or grading). The longest, branchiest flow in the app.

1. Create the purchase

Raw Cards → Add Raw Purchase. Choose the purchase type:

  • raw — a single named card. Each raw order = 1 card.
  • bulk — a lot of N cards bought together. Quantity matters; individual identification happens during inspection.

When status flips to received, the system creates a matching card_instances row in purchased_raw status. raw orders = one row at qty=1; bulk = one row at qty=N to be split during inspection.

CSV imports follow the same logic. A type=raw imported row auto-creates a card_instance; bulk does not (it stays a lot pending intake).

2. Inspect

Raw Cards → Inspection Panel. Pick a lot. For each split:

  • Set condition (NM, NM-, LP, LP+, MP, MP-, HP, DMG).
  • Set decision: Sell Raw or Submit to Grading.
  • Optional: condition notes, image, location.

Each (condition + decision) becomes its own card_instances row. The bulk row's quantity goes down as you split. Cost is allocated proportionally.

3a. Sell raw

If you decided Sell Raw, the card is now in raw_for_sale status. You can:

  • List it on eBay (Listings → Add Listing).
  • Take it to a card show (Card Shows → Add to Card Show).
  • Record a sale directly (Sales → Record Sale).

Selling moves status to sold and writes a sales row with total_cost_basis snapshotted from the card's purchase_cost.

3b. Submit to grading

If you decided Submit to Grading, see Grading Submission for the batch flow.

4. Track the outcome

Raw Cards → Raw Overall shows every raw lot with its sub-row breakdown: split routing, sold counts, revenue, and what's still in flight. Graded children don't appear here — they live in Graded/Slabs as their own inventory.

Common edge cases

  • Bulk order received but never intaked: the Awaiting Intake row on the Dashboard tells you how many cards from received bulk lots haven't been split yet.
  • Wrong condition assigned: edit the row in Raw Overall. Cost basis stays correct since condition isn't a cost driver.
  • Card lost or damaged: set status to lost_damaged. Terminal — cost is written off and excluded from P&L.
  • Wrong purchase cost on the lot: edit the parent raw_purchase. Child card_instances do NOT auto-update (would invalidate sold rows). Adjust manually if needed.
